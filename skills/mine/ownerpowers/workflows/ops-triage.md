# 运维排查线 · ops-triage（tier-aware）

> triage 判为"运维排查线"后读取。排查类**不强制提交**——给结论即可结束（早退分支）。遵守决策点门控与不可逆护栏。

## T0 直做（一眼可见：明显笔误 / 配置错）

定位 → 修 → 跑验证 → 交。无决策点，🚧 护栏仍在。

## T1 轻纪律（非显而易见的 bug）

1. `step-B` 按报错堆栈反查 / 按现象定位
   - 需大量探查但只取一个结论 → 按 `policies.md` 派 subagent **卸载探查**（省主上下文）
2. 非平凡 bug 走根因调查（见 `disciplines.md`），别跳到修复
3. `[数据问题?]` `step-D` 委托 sql-expert-dba 查数 / 诊断
4. `step-F` 产出结论（根因 + 影响面 + 修复建议）
5. 修复 → `step-C` 构建自测（带本轮新鲜证据）
6. **★决策点②（停）**：摊 diff + 提交计划，等拍板
   - 只需结论、不改代码 → 摊结论后**早退**（产出已落 `docs/problem/`）
7. `step-E` 提交；`[改 Controller 接口?]` `step-A` 回归同步 Apifox

## T2 全纪律（同一 bug 已修 ≥2 次 / 不可逆 / 高风险 / 需结构化设计）

1. **根因调查强制**：读完报错 → 稳定复现 → 查最近改动 → 多组件先在边界打日志定位断点层 → 写下**单一假设**做最小验证（见 `disciplines.md`）
   - 多组件边界排查 → 按 `policies.md` 派 subagent
2. `step-B` 定位；`[数据]` `step-D`
3. `step-F` 产出结论
4. **★决策点①（停，"根因定调"）**：摊根因 + 修复方案，等拍板
   - 修复方案复杂 / 需结构化设计：`grilling` 脑暴 → `spec-architect` 出修复 spec（在①确认前完成）
   - 只需结论 → 早退
   ───── 经①放行 ─────
5. 实现修复：先写**复现该 bug 的失败测试** → 只修根因、一次一处，不夹带"顺手改"
6. `[涉 DB?]` `step-D` → `step-C` 构建自测 + 回归测试
7. **★决策点②（停）** → `step-E` 提交 → `[改接口?]` `step-A`

## 早退分支（排查线特性）

排查的核心交付是 `step-F` 的结论（根因 + 影响面 + 修复建议）。只需结论不改代码 → 摊完结论即结束，产出落 `docs/problem/` 可追溯可复盘，**不强制走到提交**。

## SDD 委托契约

与 `feature-dev.md` 相同：声明"仅交付 spec、B 分支显式停止、不要衔接编码、交还控制权"。
