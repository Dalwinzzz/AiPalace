# 两项能力策略 · worktree 与 subagent

> 按需自动触发，不必等用户开口。探针埋在 `references/step-B-code-locate.md`（定位后判是否派 subagent）与 `references/step-C-build-test.md`（T2 需求线进编码前判是否起 worktree）。

## worktree 隔离

**触发**：T2 需求开发线（复杂 / 多步、需隔离）自动起；并行处理多个互不依赖任务时各起一个。T0 / T1 在当前工作区直做，不起。

**分支命名硬规范**（不符即错）：

```
<工具>/<类型-taskName>/<日期_版本号>
```

- 工具 ∈ `claude` / `codex`（谁在干）
- 类型 ∈ `feature` / `fix` / `refactor`，与 taskName 用**连字符 `-`** 连
  （冒号 `:` 被 git ref 规则拒绝，`git check-ref-format` 实测 invalid）
- 末段 `YYYYMMDD_vX.Y.Z`，用 `_` 连
- taskName 可中文

示例：`claude/feature-体检预约改版/20260620_v1.2.1`、`codex/fix-大屏数据对不上/20260620_v1.0.0`

建分支前可 `git check-ref-format --branch '<name>'` 自检。

**执行方式**：起 worktree / 派分支这个动作壳可逆 → 自动做，不停，但播报一行"已在 worktree `<path>` 起分支 `<name>`"。
⚠️ worktree 内的**代码改动本身仍走档位门控的决策点①②**，不因 worktree 自动化而放行。

## subagent 调度

**触发**（任一即可）：

1. **探查卸载**（最常用 · 保护主上下文）：任务要大量探查 / 检索 / 通读，但只需要一个结论 → 派单个 subagent 去探，主线只接结论。**任何档位都适用**，T0/T1 探查重时照样派。
2. **并行 fan-out**：2+ 互不依赖的子任务（独立模块 / 文件组，无共享状态、无顺序依赖）→ 并行多 subagent。一般 T2。
3. **状态文件协同**：有顺序依赖但能用共享状态文件维护过程状态的 → 先建好状态文件再派，主 agent ↔ subagent 经文件来回。紧耦合、需高频实时来回的不适用，主线串行直做。

**配置**：模型一律 `opus`；`effort` 按复杂度给（简单探查低、复杂分析/实现高）。

**纪律**：每个 subagent 任务边界清晰、产出可独立验证或落到状态文件；主控汇总后**看 diff / 读状态文件核对实际产出**，不轻信"成功"自述。

### 🚧 外派禁区（全档通用）

**决策不外派。** subagent 只能去**查事实**、**跑执行**、**收集证据**，不能替用户拍板，也不能替用户回答本该在决策点问出去的问题。

具体地说，下面这些**必须回到主线由用户本人回答**，派 subagent 去"顺便定了"即为违规：

- 决策点① 要摊的方案 / 根因定调，决策点② 要摊的提交计划
- `grilling` 的每一问（**派个 agent 去自问自答，等于这一轮 grilling 从没发生过**）
- T3 里标「必须有你在场」的条目（`grilling` / `prototype` 型）
- 任何触发 🚧 不可逆护栏的动作

判据一句话：**subagent 带回来的应该是"我查到 / 我跑完了什么"，不是"我决定了什么"。**
如果一个 subagent 的产出里出现了本该由用户拍板的选择，那个选择作废，回主线重问。
