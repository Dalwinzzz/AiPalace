# Spec 模板 · 一份好 spec 需要哪些部分

> 本文件回答的是 **"要有哪些部分、每部分要解决什么问题"**，不规定每部分怎么写。
> 结构按任务实际形态裁剪：**不适用的章节直接省略，不要留空标题**；需要展开的充分展开。

---

## 必备部分（任何复杂度都要有）

| 部分 | 它要回答什么 | 判定"写好了"的标准 |
|------|-------------|-------------------|
| **元信息** | 什么时候、给谁（哪个工具）、多复杂、在哪个代码库生成的 | frontmatter：`generated` / `target_tool` / `complexity` / `workspace` |
| **概述** | 谁在用、要新增或改变什么能力、为什么做 | 读完能回答"不做会怎样"；2-3 句，不复述任务清单 |
| **范围内 / 范围外** | 这次做什么、明确不做什么 | 范围外不是客套，是给执行者的刹车 |
| **勘察结论** | 代码现状是什么样：真实入口、链路、关键文件 | 全部是**扫过的真实路径**；推断的标 `[推断]`，没扫的不写 `已确认` |
| **实现设计** | 打算怎么改，关键决策及其理由 | 是决策，不是概念描述；能看出"为什么选这个而非那个" |
| **实施步骤** | 按什么顺序做，每步改哪些文件、怎么验证 | 每步有目标 / 主要文件 / 变更内容 / 验证方式；顺序有依据 |
| **验收标准** | 怎么算做完了 | 每条是 yes/no 可判定的客观事实，不是"能正常工作" |

## 按需追加的部分

| 部分 | 什么时候需要 |
|------|-------------|
| **术语表** | 需求引入了领域专有术语或缩写；术语全是常识就不写 |
| **全局约束** | 存在适用于**每一个**步骤的硬规则（安全策略、不改动范围、框架约定）；只约束单步的写进那一步 |
| **覆盖矩阵** | 涉及**多个**入口 / 表 / 调用链时——它的唯一价值是防遗漏。单接口单表的小改动不要画 |
| **待确认项** | 兜底记录。正常情况勘察期的歧义应当场问掉，本节通常为空或 ≤2 项（用户主动推迟的） |
| **测试方案** | 改动有行为变化时：核心场景 / 边界异常 / 回归三类各给几条 |
| **假设** | 存在影响实现的前提假设，且无法在本轮验证 |
| **DDL** | 涉及表结构变更 → 单独出 `{task-name}-ddl.sql`，spec 内只描述意图 |
| **目标架构图** | 架构级任务 → Mermaid flowchart，遵守 `references/mermaid-style-guide.md` |

## 复杂度对应的产物形态

| 复杂度 | 形态 |
|--------|------|
| Small | 单文件 `{task-name}-spec.md`，只保留必备部分 |
| Medium | 单文件，必备 + 覆盖矩阵 + 测试方案 |
| Complex | 目录 `{task-name}/`：`README.md`（索引 + 阶段依赖 + 全局约束）+ `00-overview-spec.md`（问题定义 / 目标架构 / 阶段边界）+ `NN-{phase}-spec.md`（每阶段一份，按 Medium 结构写） |

## 目标工具差异

**Claude Code**（Subagent 并行）
- 可并行的 Step 标 `[可并行]`；标之前确认两个 Worker 不会写同一文件或同一数据结构。
- 派给 Subagent 的每段内容必须**自包含**——Subagent 读不到主线程上下文，需要业务背景、代码现状、变更要求、不得修改的范围、验证方式五样齐全。
- 没有真正的并行场景就不要硬写并行分组。

**Codex**（线程内顺序执行）
- 重点在覆盖完整性与实施顺序，不需要并行标注。
- Spec 需含全局可读性要求：新增/修改方法补 JavaDoc（一句话说明用途）；关键业务分支、兼容处理点、策略分发点、易错逻辑加行级注释，注释讲"为什么"而非"是什么"。

## 落档前扫一眼

- 每条规则两个不同的人读完会写出一样的分支逻辑吗？
- 依赖 / 顺序里提到的 Step 都真实存在吗？
- 可选章节是**省略**了还是留了空标题？
- `已确认` 与 `[推断]` 标注诚实吗？
- 覆盖矩阵里的每个变更点都在某个 Step 里落地了吗？
