# 通用审查维度（commit-review 的准绳）

> 这是每次代码审查的**判据基线**。派发 reviewer 时，本文件全文内联进子代理提示。
> 判据讲"看什么、怎么算问题"，不是逐条打勾的问卷——用它引导注意力，别机械套用。
>
> 三类维度：
> - **核心必过（12 维）**：每次审查都要过一遍。
> - **固定次要（1 维）**：代码风格——每次看，但发现的问题**一律归 🟢 次要（可选）**。
> - **条件维度（命中才用）**：并发、栈相关视角——**不计入必过**，只在触发条件命中时才审。

---

## 核心通用维度（每次必过）

### 1. 正确性与逻辑
- 实现是否真的达成 commit message 声称的意图？有无声称做了但 diff 里没做（或做反）的地方？
- 边界条件：空集合 / 0 / 负数 / 超长 / 首末元素；off-by-one。
- 条件分支：每条分支都可达且正确？有没有漏掉的 else / default？
- 返回值与异常路径：错误分支的返回是否正确，会不会把失败当成功往下走？

### 2. 空值与防御
- NPE 风险点：链式取值、外部返回、Map.get、集合首元素。
- 外部输入（入参 / 请求体 / 配置 / 上游响应）是否校验？非法值如何兜底？
- 默认值是否合理，会不会用默认值悄悄掩盖了错误。

### 3. 错误处理与资源
- 异常是否被吞（空 catch / catch 后只打日志继续）？catch 范围是否过宽（吞掉了不该吞的）？
- 资源（连接 / 流 / 锁 / 文件句柄 / 线程池）是否在所有路径（含异常）释放？try-with-resources / finally。
- 失败是否可观测：日志是否带够上下文（关键 ID、入参摘要），还是只有一句 "error"。

### 4. 事务与数据一致性
- **事务管理**：`@Transactional` 覆盖范围、传播行为、只读标记；**自调用导致事务失效**；事务里混远程调用 / 大循环拖长事务。
- **幂等性**：接口 / 消费者重复触发是否安全；防重复提交。
- **业务数据一致性**（按变更牵涉范围分档看）：
  - **仅涉及单模块功能**：审该模块**内部整体业务数据一致性**——状态字段与关联明细是否同步更新、聚合/汇总值与明细是否对得上、一次业务操作涉及的多张表是否在同一事务内保持一致，不会出现改了主表漏了从表。
  - **涉及多模块**：审**模块之间冗余 / 反范式字段的一致性**——同一份数据在多个模块各存了一份副本时，本次改动是否让所有副本同步更新；跨模块的冗余字段（如另一模块缓存的名称 / 状态 / 计数）会不会因本次改动而对不上。

### 5. 数据与持久层
- SQL 正确性：条件、join、分组、去重；有没有漏 where 造成全表更新/删除。
- 性能：N+1 查询；大表无索引扫描；未分页的全量加载；循环里逐条查库。
- 批量操作：批大小是否可控，是否会一次性撑爆内存 / 超包大小。
- Schema 变更：迁移脚本是否可回滚、是否兼容存量数据、上线顺序（先加列后用列）。
- 多数据库方言差异（如 MySQL + Kingbase 双库）：函数、分页、大小写、类型、SQL 是否两库都成立。

### 6. 安全
- 注入：SQL 拼接（MyBatis `${}`）、命令拼接、模板、反序列化不可信数据。
- 越权：水平越权（改别人数据）、垂直越权（越过角色）；查询是否带上租户 / 归属过滤。
- 鉴权认证：新接口是否漏挂鉴权；token / 会话校验。
- 敏感信息：密钥 / 密码 / token 硬编码；PII / 凭证写进日志或返回体。

### 7. API 契约与兼容
- 对外接口（REST / RPC / 消息）签名、字段、枚举、错误码的变更是否**向后兼容**；删字段 / 改类型 / 改语义要特别警惕。
- 幂等语义、分页契约、时间/金额/单位约定是否一致。
- 接口文档 / 契约（如 Apifox）是否同步更新。

### 8. 性能与资源占用
- 热点路径的时间复杂度；有没有把 O(n) 写成 O(n²)。
- 循环内做 IO / 远程调用 / 查库；能否批量或缓存。
- 大对象常驻、无界集合、无上限缓存导致的内存风险。
- 缓存正确性：击穿 / 穿透 / 雪崩、与库的一致性、失效策略。

### 9. 可维护性与可读性
- 命名是否表意；有没有误导性命名。
- 重复代码（DRY）——但也别鼓励**过早抽象**，两三处相似未必要抽。
- 函数 / 类是否过长过杂，圈复杂度是否失控。
- 魔法值（散落的数字 / 字符串）是否该提常量。
- 注释是否解释"为什么"而非复述"是什么"；有无死代码 / 注释掉的代码。

### 10. 测试
- 新增 / 改动的行为是否有测试覆盖。
- 测的是**真实行为**还是 mock 自证（断言全打在 mock 上没意义）。
- 是否覆盖边界与失败路径，而非只有 happy path。
- 是否补了针对本次 bug 的回归测试。

### 11. 可观测性与运维
- 关键路径是否有日志 / 埋点 / 审计；日志级别是否合理。
- 是否需要监控指标 / 告警。
- 配置是否外置（而非硬编码）；开关 / 灰度 / 降级是否具备。

### 12. 变更卫生
- 提交是否聚焦：有没有夹带与本次意图无关的改动。
- 有无调试残留：`System.out` / `console.log` / 临时断点 / `TODO` / 被注释掉的代码块。
- 有无误删（删了看似无用实则被引用的代码 / 配置）。
- 关联文档 / 配置 / 版本号是否同步更新。

## 固定次要维度（每次看，问题一律归 🟢 次要 / 可选）

### 13. 代码风格与团队规范
- 本次改动是否符合**现有团队代码规范**：命名风格、缩进 / 大括号、包结构、注解用法、分层约定、日志格式、返回体包装等——**以仓库现存代码的既有约定为准**（看周边同类代码怎么写），不是套外部通用规范。
- **严重度固定**：本维度发现的一切问题**一律标 🟢 次要（可选优化）**，作为**建议项**列出，是否修改由作者自行决定，不因风格问题给出"必须修复"或"建议修复"。
- 不要为了凑数硬挑风格问题；确实与团队约定不一致才提。

## 条件维度（命中才用，不计入每次必过）

只在触发条件命中时才审；未命中就在报告"审查维度覆盖"里标"本次不适用"并一句话说明。

### 并发（仅当任务目标明确涉及并发时才审）
**触发条件**：commit message / 用户给的审查意图**明确指向**并发场景——如高并发、秒杀 / 抢购 / 抢号、防超卖、多线程 / 线程池改造、分布式锁、竞态修复等。未明确指向并发，则**不主动**以并发维度挑问题（默认不适用）。

命中后审：
- 共享可变状态是否线程安全（单例字段、静态变量、非线程安全集合、缓存）。
- 竞态条件：check-then-act、读改写是否原子。
- 并发资源竞争：库存 / 名额 / 计数是否防超卖、防并发覆盖（乐观锁 / 唯一约束 / select for update / 分布式锁）。
- 锁粒度与死锁风险；锁与事务的边界关系。

### 栈相关视角（ZhiJin · 落到对应技术栈才用）
被审改动落在对应技术栈时才套用，不适用就跳过：

- **Spring**：`@Transactional` 自调用失效、传播 / 只读标记；Bean 作用域与单例字段并发；条件装配 / 配置绑定。
- **MyBatis**：动态 SQL 注入（`${}` vs `#{}`）；`resultMap` 映射错漏；`foreach` 批量与 SQL 长度上限；一二级缓存陷阱。
- **双库（MySQL + Kingbase）**：SQL 方言、函数、分页、保留字、大小写敏感——同一条 SQL 两库是否都成立。
- **若依 / framework 边界**：是否越层改了公共 / framework 层；有没有绕过既定分层。
- **Activiti 工作流**：流程节点 / 网关 / 变量 / 会签的改动是否破坏既有流程实例。
- **编译铁律**：改动公共 API / 接口签名是否引发跨模块连锁编译问题（改了但没跟着改调用方）。

> ZhiJin 平台工程约定的完整口径以项目 memory（`vault/memory/01-PROJECTS/enterprise/zhijin/`）为准，本节只列审查时最常踩的点。

## 严重度校准

不是所有问题都是"严重"。按**真实影响**分级，别通胀：

- 🔴 **严重（必须修复）**：bug、数据丢失 / 损坏风险、安全漏洞、功能被破坏、线上会炸。
- 🟡 **重要（建议修复）**：架构问题、缺失功能、错误处理缺口、测试缺失、数据一致性隐患、明显性能隐患。
- 🟢 **次要（可选优化）**：微优化、文档润色，以及**代码风格与团队规范（维度 13）的一切问题——恒为此级**。

> **代码风格恒为 🟢**：无论看着多别扭，风格 / 规范类问题都不升级为 🟡 或 🔴，只作可选建议。真正影响正确性 / 可维护性到需要改的，归到对应的正确性 / 可维护性维度，而不是"风格"。

**报告不写优点 / 表扬，也不写旁白式点评**——只留结论、问题、可操作建议（真实使用反馈）。
若发现偏离 commit 意图，明确点出让作者确认是否有意为之；若是需求本身的问题（而非实现问题），也直说。
