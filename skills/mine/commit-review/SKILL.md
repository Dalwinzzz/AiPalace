# commit-review · 指定 commit 的中文代码审查报告

对 git 上**指定的一个或多个 commit** 做结构化审查，最终交付一份**去 AI 味的中文 md 报告**。
审查由子代理执行、**中文直出**，强制按本 skill **内置的通用审查维度**（准绳）逐项审；
成稿再经 `humanizer-zh` 润色叙述文字。

本 skill 只做编排 + 准绳索引，审查细则在 `references/*.md` 按需读取。

## 工作流总览

| Step | 动作 | 详细 |
|------|------|------|
| 1. 解析区间 | 把用户给的 commit 输入换算成 `BASE..HEAD` 审查区间 | 下方「Step 1」 |
| 2. 采集上下文 | commit 列表/消息、`diff --stat`、变更文件、审查意图 | 下方「Step 2」 |
| 3. 派发 reviewer | 用 general-purpose 子代理按内置维度**中文**产出报告并落盘；大 diff 深探、跨多模块并行派发 | [references/reviewer-prompt.md](references/reviewer-prompt.md) |
| 4. 润色 | 调 `humanizer-zh` 对报告**叙述文字**去 AI 味，结构/代码/结论保持原样 | 下方「Step 4」 |
| 5. 落盘 | 报告写至 `<git根>/docs/commit-review/{yyyy-mm}/{dd}/` | 下方「Step 5」 |

进每一步先用一行播报"现在在 [Step X] · [做什么]"，让用户随时可打断。

## Step 1 · 解析输入 → 审查区间

先把输入换算成 `BASE_SHA`（不含）与 `HEAD_SHA`（含），并列出被审 commit：

| 输入形态 | 换算 | 报告形态 |
|----------|------|----------|
| 单个 sha `C` | `BASE=C~1`，`HEAD=C` | 单区间 |
| 显式区间 `A..B` | `BASE=A`，`HEAD=B`（git range 语义，不含 A） | 单区间 |
| 含起点 `A^..B` / "从 A 到 B（含 A）" | `BASE=A^`，`HEAD=B` | 单区间 |
| 多个 sha，且**首尾相连**（父子链） | `BASE=first~1`，`HEAD=last` | 单区间（报告含各 commit 概览） |
| 多个 sha，**不连续** | 每个 `sha~1..sha` 单独审 | **逐 commit 分节** |
| 无参数 | 默认审最新一次提交 `HEAD~1..HEAD`，并**明说**这是默认 | 单区间 |

连续性判定：`git rev-list --parents` 检查是否构成单链；不确定就用 `git log --oneline BASE..HEAD` 核对被审 commit 是否正好等于用户列出的集合，有出入就问一句。

```bash
# 单 sha 示例
C=<sha>; BASE=$(git rev-parse "$C~1"); HEAD=$(git rev-parse "$C")
git log --oneline "$BASE..$HEAD"
git diff --stat "$BASE..$HEAD"
```

## Step 2 · 采集上下文

供 reviewer 判断"实现是否对齐提交意图"：

- **被审 commit 列表 + 完整 message**：`git log "$BASE..$HEAD"`——commit message 即本次审查的"需求/意图"基线。
- **变更概览**：`git diff --stat "$BASE..$HEAD"`（文件数、增删行）。
- **额外上下文**：若用户随手给了需求/工单/关注点，一并带给 reviewer；没有就以 commit message 为准，不要臆造需求。
- **评估 diff 体量**（决定 Step 3 派发策略）：从 `--stat` 判断是否"大 diff"——经验阈值 **变更文件 ≥ ~10 或增删 ≥ ~500 行，或跨多个独立模块/区域**。大 diff 的探查中间过程量大，正是子代理该扛的活。
- **判断牵涉范围**（决定维度 4 数据一致性怎么审）：本次改动**只落单模块**还是**跨多模块**——单模块看模块内部业务数据一致性，多模块加看模块间冗余字段一致性。

## Step 3 · 派发 reviewer 子代理

**为什么强制走子代理**：审查要读大量文件、追调用链，中间分析量大且一次性——留在子代理里消化，主线只接「探查目标 + 结论」，保住主上下文。主代理不自己边看 diff 边写报告。

读取 [references/reviewer-prompt.md](references/reviewer-prompt.md) 填好占位符后，用 **Agent 工具（`subagent_type: general-purpose`）** 派发。按 Step 2 评估的体量选策略：

| diff 体量 | 派发策略 |
|-----------|----------|
| 常规 | **单个** reviewer 子代理，走完整骨架产出报告。 |
| 大 diff（单区间、逻辑相关） | **单个** reviewer 子代理，提示里要求它**深度探查**（读改动文件与上下游、追调用链），中间分析**自行消化**，报告里只落"探查目标 + 结论 + 具体问题"，不回吐原始探查过程。 |
| 大 diff 且**跨多个独立模块/区域** | 按模块/区域**拆分并行派发多个** reviewer 子代理，每个只审自己那块并各写一段；主代理**汇总合并**为一份报告，顶部给统一结论。 |

要点（所有策略通用）：

- **中文直出**：reviewer 用简体中文写整份报告。
- **准绳内联**：把 [references/review-dimensions.md](references/review-dimensions.md) 的内容读出来，填进提示的 `{REVIEW_DIMENSIONS}` 占位（子代理看不到本 skill 的文件，必须内联）。
- **只读**：reviewer 不得改动工作树/index/HEAD；要看某版本用 `git show` 或 `git worktree add` 到临时目录。
- **落盘**：reviewer 直接把报告写到 Step 5 目标路径；并行多子代理时各写临时片段，由主代理合并落终稿。

## Step 4 · humanizer-zh 润色

reviewer 产出的报告落盘后，调用 `humanizer-zh` skill 对**目标文件就地润色**，并明确传达保留约束：

**润色**（去 AI 味）：总体结论的理由、每条问题的"为何重要"、改进建议等**叙述性文字**。

**原样保留**（不许改）：
- 代码块、`file:line` 引用、SQL/命令片段
- 严重度标签（🔴/🟡/🟢）与「可否合入」结论关键词（是/否/修复后可合入）
- 元信息头、章节标题、表格结构、审查维度覆盖清单

> humanizer-zh 用 Edit 做**定点**改写而非整篇重写，天然贴合"只动叙述、不动骨架"。若它倾向大改结构，在调用指令里再强调一次上面的保留清单。

## Step 5 · 落盘

**路径**（对齐 spec-architect 的 docs 惯例）：

```
<当前 git 仓根>/docs/commit-review/{yyyy-mm}/{dd}/{slug}-review.md
```

- `{slug}`：单区间用 `HEAD` 短 sha（如 `1a1719a-review.md`）；区间用 `base短..head短`；逐 commit 分节时用 `多提交-N笔`。
- 目录不存在就 `mkdir -p`。

**报告结构**（reviewer 按此产出，Step 4 只润色不改骨架）：

```markdown
# 代码审查报告 · {slug}

> 审查区间：{BASE短}..{HEAD短}
> 被审提交：{短sha + 首行message，逐条}
> 变更概览：{N} 文件，+{X}/-{Y}
> 审查时间：{yyyy-mm-dd}
> 审查依据：commit-review 内置通用审查维度

## 总体结论
**可否合入：** 是 / 否 / 修复后可合入
**理由：** {1–2 句技术判断}

## 问题
### 🔴 严重（必须修复）
### 🟡 重要（建议修复）
### 🟢 次要（可选优化）
> 每条：`file:line` · 问题是什么 · 为何重要 · 怎么修（不显然时给）

## 改进建议
{代码质量/架构/流程层面的**可操作**建议；没有就写"（无）"，不硬凑}

## 审查维度覆盖
{逐维度标注：已覆盖 / 本次不适用（并说明），体现"准绳"落到实处}
```

**报告只留干货，不写评论性叙述**（真实使用反馈）：
- **不写"优点/亮点"段**——审查报告不是表扬信，读者要的是待办，不是肯定。
- **不写旁白式说明**——如"某 merge 为干净合并、其携带的 X 改动属另一主题不在本轮范围"这类编辑性评论不要单独成段。出范围的事实若必须交代，在头部「被审提交」里给该 commit 一句话短标注（如 `620ee5aa 干净合并，无自有改动`）带过即可。
- 每一行都应是**结论、问题、或可操作建议**；读着像"点评/感想"的句子就删。

落盘后向用户报一行：报告路径 + 一句话结论（可否合入 + 关键问题数）。

## 内置通用审查维度（准绳 · 索引）

完整判据见 [references/review-dimensions.md](references/review-dimensions.md)。分三类：

**核心必过（每次都过）：**
1. 正确性与逻辑（是否实现 commit 意图、边界条件）
2. 空值与防御（NPE、外部输入校验）
3. 错误处理与资源（异常吞没、资源释放、失败可观测）
4. 事务与数据一致性（事务边界/传播/自调用失效、幂等；**单模块→模块内部整体业务数据一致性，多模块→模块间冗余字段一致性**）
5. 数据与持久层（SQL 正确性、N+1、索引、迁移/回滚、双库方言）
6. 安全（注入、越权、敏感信息泄漏、鉴权）
7. API 契约与兼容（对外签名变更、向后兼容、错误码）
8. 性能与资源占用（热点复杂度、循环内 IO、缓存一致）
9. 可维护性与可读性（命名、重复、复杂度、魔法值、注释讲 why）
10. 测试（覆盖真实行为、边界、回归）
11. 可观测性与运维（日志/审计、监控、配置外置、降级）
12. 变更卫生（聚焦提交、无调试残留、无误删、文档同步）

**固定次要（每次看，问题恒为 🟢 可选建议）：**
13. 代码风格与团队规范（以仓库现存约定为准，只作可选建议，不升级严重度）

**条件维度（命中才用，不计入必过）：**
- 并发（**仅当任务目标明确指出并发场景**才审：高并发/防超卖/多线程/竞态/分布式锁；未指向并发则默认不适用，不主动挑）
- 栈相关视角（Spring/MyBatis/双库/若依 framework/Activiti/编译铁律——落到对应栈才用）

## 硬约束（违反则阻断流程）

1. **只读审查**：reviewer 与本流程全程不改工作树/index/HEAD/分支；越权改动即中止。
2. **中文直出**：报告中文成稿，不走"英文→翻译"路径（避免术语失真）。
3. **准绳内联**：派发时必须把 review-dimensions 内容内联进子代理提示，不能只丢路径。
4. **意图不臆造**：审查基线是 commit message（+ 用户所给上下文），不凭空编造需求。
5. **润色保结构**：humanizer-zh 只动叙述文字，代码/引用/严重度/结论/表格原样保留。
6. **落盘规范**：报告落在 `<git根>/docs/commit-review/{yyyy-mm}/{dd}/`，不散落到别处。
7. **维度分级照准绳**：并发**仅任务目标明确涉及时才审**（非必过，未指向不主动挑）；代码风格问题**恒为 🟢 次要（可选建议）**，不得升级严重度。
8. **大 diff 走子代理深探**：变更体量大 / 跨多模块时，探查交给子代理（必要时并行拆分），主线只收目标+结论，不把海量中间分析拉进主上下文。

## 反模式

- ❌ 主代理自己边看 diff 边写报告（丢了干净上下文与只读隔离）。
- ❌ reviewer 只给"看起来不错"的泛泛结论，不落 `file:line`、不分严重度。
- ❌ humanizer-zh 把严重度标签、结论关键词、代码块也一起"润"没了。
- ❌ 把不连续的多个 commit 硬塞进一个区间 diff（混入无关中间提交）。
