# creations.md — 创作性产物规范

> 本文档定义 AiPalace 创作性产物（creations）的归档规则、命名约定与元数据规约。  
> 最高准绳：[`PHILOSOPHY.md`](../../PHILOSOPHY.md)（P1–P9）。

---

## 1. 定位

**creations** 是 AiPalace 管理的第三类产物，与内容资产（content-assets）和产品资产（product-assets）**正交单列**：

- 不挂载至任何工具挂载点（`~/.claude/`、`~/.codex/`）
- 不耦合 `skillctl`、registry 等工具链
- 纯产出存档——AI 辅助生成的创作性成品，以本仓库为唯一归档地（体现 [P1](../../PHILOSOPHY.md#p1--单一真源sot)）

**与 `docs/skills` 的边界**：

| 维度 | skills（内容资产） | creations（创作性产物） |
|------|-------------------|------------------------|
| 性质 | 能力单元（可调用的 AI Agent 行为） | 创作成品（图像/精灵/媒体等产出物） |
| 工具派生 | 由 `skillctl` symlink 派生到双工具 | **不派生**，原地归档 |
| registry 管理 | 必须在 `registry.yaml` 登记 | **不登记** registry |
| 触发与调用 | 通过 `/` 斜杠菜单被 Agent 调用 | 不被 Agent 调用，供人直接取用 |

> 若某产出物既是创作成品又需作为 skill 能力暴露（极少见），应在 `skills/` 创建对应 skill 条目，`creations/` 只作归档，两者相互引用但不合并。

---

## 2. 目录结构

创作性产物统一存放于仓库根目录下的 `creations/` 目录：

```
creations/
└─ <creation-id>/          # 作品 ID（小写 kebab-case）
   ├─ pet.json             # 元数据文件（规约见第 4 章）
   ├─ v1/                  # 版本目录（见第 3 章）
   │  ├─ spritesheet.webp  # 主产出文件（格式见第 5 章）
   │  └─ ...（其他相关文件）
   ├─ v2/
   ├─ ...
   └─ vN/                  # 最新版本
```

**示例**：`creations/mon3tr-codex/`——Mon3tr Codex 桌面宠物精灵，各版本迭代归档。

---

## 3. 版本命名

版本目录使用 **`v1` → `v2` → … → `vN`** 的顺序整数命名，单调递增，不允许删除或重排已有版本目录：

- 每次对产出物的实质性修改（如重新生成 spritesheet、调整设计方案）新增版本目录
- 版本目录内的文件是该版本的**完整快照**，不修改已归档版本的内容（体现 [P8](../../PHILOSOPHY.md#p8--决策留痕诚实标注) 的留痕精神）
- 最新版本即版本号最大的 `vN/` 目录
- 轻微修正（如修正文件名、补充 preview）可在同版本目录内追加，不新建版本

**版本 vs 作品级元数据**：`pet.json` 放在 `<creation-id>/` 根，反映最新版本的概要信息；各 `vN/` 内的具体产出文件才是版本快照实体。

---

## 4. 元数据规约（`pet.json`）

每个作品根目录下必须存在 `pet.json`，字段约定如下：

```json
{
  "id": "<creation-id>",
  "displayName": "<展示名称>",
  "description": "<简短描述：外观/用途/创作背景，不超过三行>",
  "spritesheetPath": "<主产出文件的相对路径，相对于 pet.json 所在目录的最新版本>"
}
```

| 字段 | 必须 | 说明 |
|------|------|------|
| `id` | 是 | 与目录名相同，小写 kebab-case |
| `displayName` | 是 | 人类可读展示名称 |
| `description` | 是 | 简短描述外观/用途/来源，不超过三行 |
| `spritesheetPath` | 取决于类型 | 若主产出为精灵图/图像媒体，指定相对路径；非媒体类产物可省略 |

> `pet.json` 是为桌面宠物类产物（如 `mon3tr-codex`）建立的元数据格式，后续其他类型的 creations 可复用或扩展字段，不必另立格式文件。若某类产物确实无法套用 `pet.json`，可在该作品目录下添加 `README.md` 替代，并在本规范下一次修订中正式扩充字段约定。

---

## 5. 文件格式与可见性

**推荐格式**（不强制）：

| 类型 | 推荐格式 |
|------|---------|
| 精灵图 / 像素图 | `webp`（兼顾质量与体积）或 `png` |
| 预览图 / 联系表 | `png` 或 `jpg` |
| 矢量图 | `svg` |
| 音频 | `mp3` / `ogg` |

**可见性**：creations 中的所有内容随仓库一同 git 追踪，无特殊访问控制。若某作品涉及版权或敏感素材，应在该作品目录下的 `README.md` 中显式标注来源与许可证（体现 [P8](../../PHILOSOPHY.md#p8--决策留痕诚实标注)）。

---

## 6. 纳入原则

**什么应该放入 creations：**

- AI 辅助生成的创作性成品（精灵图、像素画、设计稿等）
- 与工具链无关、以归档存档为目的的媒体产出物
- 有版本迭代需求的创作过程记录

**什么不应该放入 creations：**

- 可被 Agent 调用的能力脚本 → 应放 `skills/`
- 工具配置文件 → 应放各工具对应目录
- 临时草稿（未定型的产出）→ 不纳入仓库，直至形成可归档版本
