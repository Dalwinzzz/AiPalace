## 根因（5 类报错同源，非 5 个独立 bug）

共同场景：**跑 spec-architect / writing-plans 长文档 + 多 skill 串联 + 上下文极大**时触发。

1. **主因 — `--effort max` + 满上下文顶到极限**
   `~/.zshrc.d/claude.zsh:31` 把每次会话钉成 `--effort max`。满上下文 + max thinking 把输出推到极限 → 工具调用 JSON 截断/残缺 → 解析失败 / 参数无效 / 裸 JSON 泄漏；retry 因上下文未变仍失败；推理硬扛表现为长时间卡死。session 历史普遍 ~5MB 印证上下文被堆满。

2. **次因 — node v23 非 LTS 底噪**
   v23 是奇数非 LTS 版，长连接/流式场景偶发不稳，加重 socket 异常。

3. **独立项 — Auto-update failed 是瞬时网络抖动**
   实测 `claude update` = up to date，软链指向 `versions/<版本号>` 本就是 native installer 正常形态（非损坏）。**安装健康，无需重装。**

## 复现实测修正（2026-06-10，会话 `70c593c8`）

2026-06-10 在 biz-workflow 开发会话中**精确复现**，从 jsonl 取得决定性证据，**证伪了上面"主因 = 上下文撑爆"的初判**：

| 指标 | 实测值 | 结论 |
|---|---|---|
| 报错时上下文占用 | **127.6k / 1M = 13%**（Free 87%） | ❌ 不是上下文撑爆 |
| 报错那条 output | **253 tokens** | ❌ 不是输出过长被截断 |
| 报错时模型 | **claude-opus-4-8**，`stop_reason=tool_use` | ✅ 确系 Opus 4.8 |
| 报错形态（jsonl 行 342/344 原文） | 模型把工具调用**输出成纯文本 XML 字面量** `count\n<invoke name="Bash">…</invoke>`，而非结构化 tool_use 块；retry 一字不差重犯 → `retry also failed` | **真正根因** |

**修正后的根因定性**：这是 **Opus 4.8 工具调用序列化的偶发确定性 bug**——偶发地把 tool-call 渲染进文本通道而非工具通道。特征：
- 与**上下文大小无关**（13% 也触发）
- 与**输出长度无关**（253 token 也触发）
- **retry 无效**（确定性重复同一错误输出）
- 5 张截图里 opus 的 parse 失败 / 裸 JSON 泄漏全是**此同一根**

`--effort max` 是否为诱因：本次会话 `/model` = Opus 4.8 且当时 alias 仍是 `--effort max`（大概率在 max），但 jsonl 未记 effort 字段，**"max 比 high 更易触发"未取得对照证据**——存疑，但按下方处置规避即可。
