# SYZH：活动预约时间冲突校验修正 + App 活动列表 `orderType=3` 排序修正

## 概述

本次迭代修复两个已上线链路的业务偏差：

1. `/app/courseOffline/appoint` 当前对杭州普通养育照护活动的“同一儿童同一时间段只能预约一场活动”校验不符合产品规则，尤其是冲突判定与冲突提示信息不满足业务要求。
2. `/app/courseOffline/getList` 当前 `orderType=3` 的实现是直接按活动开始时间倒序，不符合“时间由近及远”的真实业务语义；产品要求改为按活动开始时间距离当前时间的绝对时间差排序，离当前时间最近的活动排在前面。

本次目标是在不改变其他课型与既有排序语义的前提下，修正这两个分支逻辑，并保持接口协议兼容。

## 术语表

| 术语 | 含义 |
|------|------|
| 时间冲突 | 同一儿童已预约的活动时间段与当前待预约活动时间段存在真实时间重叠 |
| 边界相接 | 两个时间段首尾正好相连，例如 `8:30-9:30` 与 `9:30-10:30` |
| 时间由近及远 | 按活动 `startTime` 距离“当前时间”的绝对差值升序排序，差值越小越靠前 |
| 现有默认排序 | `/app/courseOffline/getList` 当前 SQL 查询结果顺序，加上现有距离排序分支逻辑 |

## Task 1: 修复 `/app/courseOffline/appoint` 的时间冲突校验

**目标**：让同一儿童在杭州普通养育照护活动中，无法预约任何真实重叠的时间段活动；首尾边界相接的时间段允许预约；命中冲突时必须明确返回冲突时间段。

**前置条件**：
- 当前入口为 `POST /app/courseOffline/appoint`
- 当前核心校验方法为 `validateHangzhouOrdinaryTimeConflict(CourseOffline courseOffline, CourseOfflineAppointDTO dto)`
- 当前 DAO 逻辑通过 `countChildTimeConflictAppoint(...)` 统计冲突数量
- 当前 SQL 条件是时间区间交叉判断

**核心规则**：
1. 同一儿童在同一真实重叠时间段内只能预约一场养育照护活动。
2. 时间冲突判定只覆盖“真实重叠”，不包含“边界相接”。
3. 根据本次确认后的业务口径，以下情况允许预约：
   - 已预约 `8:30-9:30`，再约 `9:30-10:30`
   - 已预约 `9:00-10:00`，再约 `10:00-11:00`
4. 因此冲突判定应采用“开区间重叠”语义，而不是含边界冲突语义。
5. 时间冲突仍以儿童身份证号作为同一儿童标识，仍排除当前待预约活动自身 `courseId`。
6. 冲突校验的课型范围保持现状，只校验当前杭州普通养育照护活动链路，不扩大到未要求调整的其他课型。
7. 当前仅返回冲突数量不足以满足业务要求；本次必须能明确返回一条冲突记录的时间段，用于拼装用户提示。
8. 若同一儿童存在多条冲突记录，只拦截一次，但必须明确返回其中一条冲突记录的预约时间段。
9. 用户提示文案必须带出冲突时间段，且文案需用户可读、业务语义明确，例如：“该儿童已预约 09:00-10:00 的活动，请选择其他时间后再报名”。
10. 冲突校验必须发生在保存预约前，一旦命中冲突，禁止报名，不进入后续预约写入流程。

**边界与异常**：
- 以下情况视为冲突：
  - 已预约 `9:00-10:00`，再约 `9:30-10:30`
  - 已预约 `9:00-10:00`，再约 `8:30-9:30`
  - 已预约 `9:00-10:00`，再约 `9:00-10:00`
- 以下情况不视为冲突：
  - 已预约 `8:30-9:30`，再约 `9:30-10:30`
  - 已预约 `9:00-10:00`，再约 `10:00-11:00`
- 如果活动时间为空，沿用现有活动数据前置校验逻辑，不在本次新增独立兜底分支。[推断]

**验收标准**：
- [ ] 已预约 `8:30-9:30` 时，再预约 `9:30-10:30` 允许通过。
- [ ] 已预约 `9:00-10:00` 时，再预约 `9:30-10:30` 会被拦截。
- [ ] 已预约 `9:00-10:00` 时，再预约 `8:30-9:30` 会被拦截。
- [ ] 已预约 `9:00-10:00` 时，再预约 `9:00-10:00` 会被拦截。
- [ ] 命中冲突时，提示中能明确看到一条冲突的时间段。
- [ ] 提示文案符合用户阅读习惯，不返回技术性错误信息。
- [ ] 除目标链路外，其他未要求调整的预约校验逻辑不回退。

**依赖**：无

## Task 2: 修复 `/app/courseOffline/getList` 中 `orderType=3` 的排序逻辑

**目标**：把 `orderType=3` 从“按开始时间倒序”改为“按开始时间距离当前时间最近排序”。

**前置条件**：
- 当前入口为 `POST /app/courseOffline/getList`
- 当前 DTO 为 `QueryH5CourseOfflineListDTO`
- 当前控制器在拿到列表后进行内存排序
- 当前 `orderType=3` 逻辑是直接按 `startTime` 倒序
- 当前 SQL 原始顺序仍存在 `order by runningState, courseId desc`

**核心规则**：
1. `orderType=3` 的真实业务语义不是“开始时间倒序”，而是“活动时间由近及远”。
2. “由近及远”明确定义为：
   - 计算每个活动 `startTime` 与当前时间 `now` 的绝对时间差
   - 按该差值升序排序
   - 差值越小，活动越靠前
3. 示例：当前时间为 4 月 7 日时：
   - 4 月 6 日活动与 4 月 8 日活动，距离当前时间都为 1 天
   - 它们应排在距离更远的活动之前
4. `orderType=3` 只修正该分支自身逻辑，不改变 `null/1/2` 的现有排序语义。
5. 排序计算基准使用服务端当前时间。
6. 排序必须在最终分页之前完成，确保分页结果与排序结果一致。
7. 若多个活动与当前时间的绝对差值相同，应保持原始结果集中的相对顺序，避免同距离活动在翻页或重复请求中出现抖动。
8. 当前 SQL 已有默认顺序，若 `orderType=3` 继续在控制器层做内存排序，则必须确保不会再叠加与之冲突的二次排序逻辑。
9. 距离排序分支与时间排序分支必须互斥；`orderType=3` 时不再参与距离升降序处理。

**边界与异常**：
- `startTime` 为空的活动若理论上不会出现在列表中，则沿用现状；若存在，应统一排在时间排序结果末尾。[推断]
- 与当前时间差值相同的过去活动和未来活动，不额外区分方向，只比较绝对差值；方向不参与主排序键。
- 若绝对差值相同，则保持当前 SQL 原始顺序作为稳定次序。

**验收标准**：
- [ ] `orderType=3` 时，列表按 `abs(startTime - now)` 升序排序。
- [ ] 当前时间附近的活动优先展示，不再是单纯按 `startTime` 倒序。
- [ ] 4 月 6 日和 4 月 8 日在 4 月 7 日请求时，会排在比它们更远的日期之前。
- [ ] `null/1/2` 的现有排序行为保持不变。
- [ ] 排序后的分页结果稳定，不出现分页前后顺序不一致。

**依赖**：无
