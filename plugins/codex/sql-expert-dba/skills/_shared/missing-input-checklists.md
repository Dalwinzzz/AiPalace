# 缺失输入检查表

各 workflow 在开始分析前，必须根据以下检查表评估输入完整度。缺少 `必须` 级别的输入时，必须先向用户反问，不得伪造确定性输出。

## 输入分级

| 级别 | 含义 | 缺失时行为 |
|------|------|-----------|
| **必须** | 缺失则无法产出可靠结论 | 必须反问用户，不得继续分析 |
| **建议** | 缺失则降级为保守分析 | 可继续，但必须在输出中标注降级原因和 `[推断]` |
| **可选** | 有则更精确 | 可继续，不影响主输出可靠性 |

---

## sql-query-optimizer

| 输入项 | 级别 | 缺失时影响 |
|--------|------|-----------|
| SQL 原文 | **必须** | 无法分析 |
| 方言 | 建议 | 无法做方言特定优化，降级为通用 ANSI 分析，标注 `[推断]` |
| 表结构 / DDL | 建议 | 无法做索引覆盖分析，只能给保守建议 |
| 索引定义 | 建议 | 无法判断索引有效性，只能推断 |
| EXPLAIN / 执行计划 | 可选 | 无法做精确的执行路径分析，只能做静态分析 |
| 数据量级 | 可选 | 无法评估性能影响的严重程度 |
| 优化目标 | 可选 | 默认以查询延迟为优化目标 |

---

## sql-error-diagnostician

| 输入项 | 级别 | 缺失时影响 |
|--------|------|-----------|
| 报错全文或错误码 | **必须** | 无法定位错误类型 |
| 触发 SQL | 建议 | 无法分析 SQL 本身的问题，只能基于错误码推断 |
| 方言 | 建议 | 无法确认错误码的方言特定含义 |
| 相关 DDL | 可选 | 无法验证约束/类型相关的根因 |

---

## sql-schema-reviewer

| 输入项 | 级别 | 缺失时影响 |
|--------|------|-----------|
| DDL（CREATE TABLE 等） | **必须** | 无法评审 |
| 业务目标 | 建议 | 无法判断设计是否匹配业务需求，只能给通用评审 |
| 主要查询场景 | 建议 | 无法评估索引设计的针对性 |
| 数据规模 | 可选 | 无法评估大表操作风险 |

---

## sql-report-query-builder

| 输入项 | 级别 | 缺失时影响 |
|--------|------|-----------|
| 业务需求描述 | **必须** | 无法理解要生成什么 |
| DDL / 表关系 | **必须** | 无法确认表名、字段名、关联关系 |
| 指标定义 | 建议 | 口径不明确时必须反问 |
| 粒度（日/月/用户等） | 建议 | 影响 GROUP BY 设计 |
| 时间范围 | 建议 | 影响 WHERE 条件 |
| 去重规则 | 建议 | 影响 DISTINCT / GROUP BY 逻辑 |
| 方言 | 建议 | 影响函数和语法选择 |

## 通用规则

1. 检查在 workflow 开始时立即执行，不等到分析中途
2. 缺少 `必须` 项时，反问措辞应简洁具体，说明为什么需要该信息
3. 多个 `必须` 项缺失时，一次性反问全部缺失项，不逐个追问
4. `建议` 项缺失时，在输出的 `待确认/推断` 段标注降级原因
